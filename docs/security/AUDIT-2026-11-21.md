# VaultZero — final security audit & penetration test

**Version tested:** 1.7.12 (versionCode 21), release APK + source at `8dd0f68`; fixes shipped in 1.7.13 (versionCode 22)
**Audit date:** 21 November 2026
**Method:** OWASP MASVS 2.1 / MASTG, static review, on-device checks, targeted fuzzing, severity triage
**Scope:** release APK, Android app source, local storage, backup import/export, biometrics, UI/platform surface, distribution artifact
**Out of scope:** OS Keystore internals, physical chip-off / cold-boot attacks, third-party library internals beyond version and configuration review

## 1. Executive summary

VaultZero's core design holds up: no network permission in the packaged manifest, item payloads are
AES-256-GCM with AAD and redacted metadata, the master key is never stored in plaintext, biometric
unlock is bound to a hardware Keystore key through `CryptoPrompt`-style `CryptoObject`
authentication, backups are excluded from cloud/device transfer, and the release build is
non-debuggable, R8-minified, and screenshot-protected.

The audit found **no Critical or High severity issues**. It found **two Medium denial-of-service
bugs in the backup import path**, both fixed and regression-tested before this report:

| ID | Severity | Title | Status |
| --- | --- | --- | --- |
| VZ-BACKUP-001 | Medium | Unbounded read of an imported backup (OOM crash) | **Fixed** |
| VZ-BACKUP-002 | Medium | Deeply nested JSON backup throws `StackOverflowError` (crash) | **Fixed** |
| VZ-BACKUP-003 | Low | Restore accepts KDF parameters below current defaults | Accepted, migration mitigates |
| VZ-BACKUP-004 | Low | Restore is not atomic across DB replace and prefs commit | Accepted |
| VZ-BACKUP-005 | Low | 8 MB import ceiling vs. uncapped export | Accepted |
| VZ-CRYPTO-001 | Info | Legacy PBKDF2 floor of 10k remains readable | Accepted (read-only, migrated) |
| VZ-CRYPTO-002 | Info | Envelope ciphertexts are not AAD-bound to their context | Hardening backlog |
| VZ-STORAGE-001 | Info | Item type/timestamps stored in plaintext metadata | Informational |
| VZ-PLATFORM-001 | Info | Exported `MainActivity` handles shortcut actions from any app | Verified gated by lock |
| VZ-RESILIENCE-001 | Info | APK signed with v2 only (no v3/v3.1) | Hardening backlog |
| VZ-MEM-001 | Info | Last copied secret retained as a String until next copy/lock | Hardening backlog |
| VZ-TEST-001 | Info | Fake Stripe fixtures in `androidTest` sources | Informational |
| VZ-AUTH-001 | Not tested | Biometric instrumentation blocked on the emulator (no secure lock screen/enrolment) | Re-run on Pixel required |

**Recommendation: GO for beta**, with two conditions:

1. Re-run `BiometricKeyBindingTest` on a device with a secure lock screen and an enrolled fingerprint
   (Pixel 9 Pro XL) before publishing; the emulator cannot create the auth-required key.
2. Track VZ-BACKUP-003 and VZ-BACKUP-004 in the hardening backlog for 1.8.

## 3. Findings

### VZ-BACKUP-001 — Unbounded read of an imported backup (Medium, Fixed)

`BackupFileIo.readText` called `input.readBytes()` and only then compared the size with
`MAX_BACKUP_BYTES`. A content provider that streams more than the limit (or an enormous user file)
allocates everything first; `OutOfMemoryError` is an `Error`, so the surrounding `catch (Exception)`
does not stop the process from dying. An attacker can hand the user a 2 GB "backup" or register a
malicious document provider.

Evidence: before fix, `BackupFileIo.kt` line 35 (`val bytes = input.readBytes()` then size check).

Fix: bounded read (`readBounded`) that stops at `maxBytes + 1` and returns null; regression tests
cover oversize and exact-limit streams.

### VZ-BACKUP-002 — Deeply nested JSON backup throws StackOverflowError (Medium, Fixed)

`importEncryptedBackup` and `restoreBackupAtSetup` parsed attacker-controlled JSON with
`JSONObject(...)` inside `catch (e: Exception)`. `org.json` is recursive descent: 20,000 nested
arrays throw `StackOverflowError`, an `Error` that escapes the catch and kills the app.

Evidence: probe test on API 34 produced `java.lang.StackOverflowError` from `JSONObject` at 20k
depth.

Fix: `BackupJson.parse` pre-scans bracket depth (limit 64, string-aware) and also catches
`StackOverflowError`, mapping both to `VaultError.INVALID_JSON`. Both parse sites use it; tests
cover 20k depth, normal envelopes, and brackets inside strings. A repository-level import test
proves `VaultException`, not a crash.

### VZ-BACKUP-003 — Restore accepts KDF parameters below current defaults (Low, Accepted)

`KdfSpec.decode` bounds Argon2id to m=8 MiB…128 MiB, t=1…10, p=1…4 and PBKDF2 to 10k…2M. A crafted
3.3 backup can declare `argon2id:8192:1:1` or `pbkdf2-sha256:10000`; `restoreBackupAtSetup` keeps that
envelope until the first successful unlock migrates both envelopes to `KdfSpec.CURRENT`
(64 MiB, t=3, p=1). Impact is limited: the attacker who crafts the file already knows its password,
and the weak envelope is short-lived; a stolen device restored from such a file has a cheaper offline
target until first unlock.

Recommendation (1.8): require `newMasterPassword` or re-wrap with `CURRENT` when the source spec is
below the current floor, or reject with a clear message. Test vectors for the weak specs are in the
audit corpus.

### VZ-BACKUP-004 — Restore is not atomic across DB and prefs (Low, Accepted)

`restoreBackupAtSetup` writes records with `dao.replaceAllForRestore(entities)` and then commits the
envelope with `prefs.saveEnvelopeCredentials(...)`. A process kill or disk-full between the two
leaves new records with old credentials (or an uninitialised vault). The user can retry the restore,
but the old vault is already replaced.

Recommendation: journal the restore (marker + previous envelope) and recover on next launch, or write
credentials first with a rollback copy.

### VZ-BACKUP-005 — Import ceiling vs. uncapped export (Low, Accepted)

Imports are capped at 8 MB (`MAX_BACKUP_BYTES`); exports are not. A vault with roughly 10k+ items can
produce a backup the app then refuses to restore. Recommendation: cap export with an explicit error,
raise the import cap, or stream-parse.

### VZ-CRYPTO-001 — Legacy PBKDF2 floor (Info)

`MIN_ACCEPTED_ITERATIONS = 10_000` remains for reading pre-1.6 envelopes; new writes use Argon2id
(64 MiB, t=3, p=1) and successful unlock migrates both envelopes. No action required beyond keeping
the legacy path read-only.

### VZ-CRYPTO-002 — Envelope AAD context (Info)

Item payloads use `recordAssociatedData(id, type)`, but VMK/recovery envelopes are encrypted without
AAD. Cross-context swaps fail today because each context uses a distinct key. Binding context (e.g.
`"ENVELOPE:PASSWORD:VMK"`) would make the format robust against future key reuse.

### VZ-STORAGE-001 — Plaintext metadata (Info)

The Room row stores id (UUID), type (`LOGIN`), timestamps, favourite flag and tags placeholder in
plaintext; title and category are `[ENCRYPTED]`/`Encrypted`, and the payload is ciphertext. This
matches the documented zero-knowledge-local model (the DB is not SQLCipher), but it is metadata the
user may care about. Confirmed by `run-as` inspection: no secret values in DB, WAL or prefs.

### VZ-PLATFORM-001 — Exported MainActivity (Info, verified gated)

`MainActivity` is exported (launcher necessity) and accepts the shortcut actions
`SHORTCUT_NEW_LOGIN` / `SHORTCUT_GENERATOR` from any app. Starting it with those actions while locked
shows the lock screen and queues the action until unlock; no editor or secret is reachable. Verified
on-device.

### VZ-RESILIENCE-001 — APK signature v2 only (Info)

`apksigner verify` reports v2 true, v3/v3.1 false. v3 enables key-rotation proofs; not required for a
self-distributed APK, but recommended before any signing-key rotation.

### VZ-MEM-001 — Retained clipboard String (Info)

`copySecurely` keeps the last sensitive value in `lastCopiedSensitiveValue` for the ownership check
and does not null it after clearing. The value stays in memory until the next copy/lock. Consider
clearing it after `clearSensitiveClipboardIfOwned`.

### VZ-TEST-001 — Fake Stripe fixtures (Info)

`androidTest` seeds a demo item with `pk_live_51Demo…` / `sk_live_51Demo…Secret` values. They are
obviously synthetic, live only in test sources, and are not packaged in the release APK. The scanner
now labels test-directory hits as fixtures.

### VZ-AUTH-001 — Biometric instrumentation not re-run (Not tested, environment)

Two `BiometricKeyBindingTest` cases fail on the API 34 emulator because `getEncryptCipher` returns
null: the emulator has no secure lock screen / enrolled fingerprint, so the auth-required Keystore key
cannot be created (`setUnlockedDeviceRequired`/`setUserAuthenticationParameters`). This is a safe
failure, not a bypass. The suite previously passed 15/15 on the Pixel 9 Pro XL; re-run there before
beta distribution.
